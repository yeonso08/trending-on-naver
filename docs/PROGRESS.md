## 1. 지금까지 한 일

### 1-1. 폰트 정리

`next/font`의 Inter를 쓰면서 `globals.css`가 `body`에 Arial을 다시 지정해 서로 충돌하고
있었습니다. 한글 폰트는 지정된 적이 없었습니다.

**Pretendard Variable**(SIL OFL 1.1, 상업적 이용 가능)로 교체하고 자체 호스팅합니다.
전체 variable 파일은 2MB라 통짜로 쓰지 않고 **동적 서브셋 92개**를 넣었습니다.
브라우저가 `unicode-range`를 보고 필요한 조각만 받습니다.

- 메인 페이지 기준 실제 다운로드: **8개 / 약 206KB** (통짜 대비 10배 절감)
- 사용 빈도 상위 3개(라틴 + 최빈 한글)는 preload
- 외부 CDN을 쓰지 않아 추가 DNS/TLS 왕복이 없습니다

### 1-2. 디자인 전면 개편

shadcn 기본값 그대로였던 초록 primary와 radius 1rem 조합이 전체를 템플릿처럼 보이게
만들고 있었습니다. 디자인 토큰부터 다시 잡았습니다.

- 헤더/푸터 셸 추가, 라이트/다크/모바일 모두 확인

### 1-8. 함께 고친 버그

- **`generateStaticParams` 이중 인코딩** — 이미 `encodeURIComponent`된 slug를 넘겨
  Next.js가 한 번 더 인코딩했습니다. **한글 검색어 페이지 10개 중 9개가 not-found로
  프리렌더**되고 있었고, 라틴 문자 검색어(`mlb`)만 멀쩡해 발견이 어려웠습니다.
- **`Loading.tsx` → `loading.tsx`** — Next.js는 소문자만 인식합니다. macOS는 대소문자를
  구분하지 않아 로컬에선 동작하는 것처럼 보였지만 Vercel(Linux)에선 적용되지 않았습니다.
- **`DeviceType`의 `'m'` → `'mo'`** — 네이버 실제 스펙은 `pc`/`mo`이고 폼은 이미 `mo`를
  보내고 있어서, 모바일 선택 시 검색 조건 표시가 `undefined`였습니다.
- **검색 폼 기본값** — 날짜가 비어 있고 연령대가 하나도 선택되지 않아 처음 열면 검증
  실패부터 보게 됐습니다. 최근 30일 + 전체 연령대로 시작합니다.
- **구글 RSS 실패가 빌드를 깨뜨리던 문제** — 조회 실패 시 예외를 던져 프리렌더 단계가
  통째로 실패했습니다. 빈 배열 반환 + 10초 타임아웃으로 바꿨습니다.
- 죽은 코드 제거: `use-trend-data.ts`(POST 라우트에 GET 호출), `trending-detail.tsx`,
  `shared/api/base.ts`와 `axios` 의존성, 잔존 `console.log`

### 1-10. 실시간성 복구 (2026-08-26)

"실시간 검색어"인데 화면의 기준 시각이 한 시간 넘게 뒤처져 있었습니다. 원인이 셋이었습니다.

1. **타임존 미지정** — `Intl.DateTimeFormat`에 `timeZone`이 없어 UTC로 도는 서버 기준으로
   포맷됐습니다. 로컬(KST)에선 멀쩡해 보여 발견이 어려웠습니다.
2. **표시 시각의 의미가 틀림** — 구글 RSS의 `pubDate`(그 검색어가 트렌드에 오른 시각)를
   "○○ 기준"으로 찍고 있었습니다. 우리가 언제 갱신했는지와 무관한 값입니다.
   서버가 실제로 데이터를 가져온 시각(`fetchedAt`)으로 바꿨습니다.
3. **ISR 캐시 정체** — `revalidate: 60`은 자동 갱신이 아니라 stale-while-revalidate입니다.
   방문자가 뜸하면 아무도 재생성을 트리거하지 않아 캐시가 수십 분씩 묵습니다.
   실측으로 `age: 2333`(39분) / `x-vercel-cache: STALE`을 확인했습니다.

3번은 두 축으로 해결했습니다.

- **`.github/workflows/refresh-trending.yml`** — 10분마다 홈페이지에 `curl`. **Vercel Hobby는
  자체 Cron이 하루 1회 제한**이라 못 쓰고, 퍼블릭 레포의 무료 GitHub Actions로 대신합니다.
- **60초 클라이언트 폴링** — `GET /api/trending`. 이미 열어 둔 탭이 새로고침 없이 갱신됩니다.
  내부 fetch가 같은 60초 캐시를 타므로 구글 RSS 호출은 늘지 않습니다. 백그라운드 탭은 건너뜁니다.

### 1-11. 트렌드 분석 페이지 개편

폼이 한 덩어리 슬래브였고, 특히 **연령대 체크박스 11개**가 화면을 지배해 투박했습니다.

'질문하고 답을 받는' 흐름으로 다시 짰습니다.

- 기간은 `7일 / 30일 / 3개월 / 1년` 프리셋. 달력은 '직접 선택'에만 남김
- 기본값이 전부 '전체'인 디바이스·성별·연령대는 접어 둠
- 빈 화면 대신 **지금 뜨는 검색어를 눌러 바로 조회**하는 입구 (사이트의 두 축을 연결)
- 결과는 칩 대신 **최고점·평균·초반 대비 후반 변화**를 계산해 표시.
  최고점은 차트 위 점으로 이어 줌
- 로딩은 스피너 대신 결과 모양 스켈레톤

폰트는 Pretendard 서브셋 전략을 깨지 않으려 새로 추가하지 않고, 크기·굵기·간격만으로

### 1-13. 브랜드 교체 (2026-08-28)

**서비스명을 '트렌드나우'에서 '키위(Keywi)'로 바꿨습니다.** 이전 이름은 실시간 순위만
가리켜서 트렌드 분석 기능을 담지 못했습니다. '키워드 순위'를 줄인 이름입니다.

로마자는 `Kiwi`가 아니라 **`Keywi`** 입니다. 철자에 `key`가 남아 어원이 스스로 드러나고,
과일 `kiwi` 및 기존 키위 브랜드들(키위플러스·키위웍스·키위디스크 등)과 검색 결과가
갈립니다. 이 표기를 되돌리면 두 이점이 한꺼번에 사라집니다.

**로고는 '지평선 위로 떠오른 반단면'입니다.** 키위 단면이면서 부채꼴 차트로도 읽혀
실시간 순위와 추이 분석을 한 형태에 담습니다. 여섯 갈래 시안을 놓고 고른 결과입니다.

- 과육 · 부챗살 · 씨앗이 톤을 달리하는 **세 겹 구조**이고 이 톤 차이가 인상을 만듭니다.
  두 색으로 줄여 네거티브로 파내 본 적이 있는데 딱딱해져서 되돌렸습니다.
- **배경 타일은 없습니다.** 심볼만 배경 위에 얹습니다. 다크 모드를 따라가도록 과육 톤을
  `--brand-flesh` 토큰으로 뽑았고, 파비콘에는 `prefers-color-scheme`를 심었습니다.
- 애플 아이콘만 배경을 깝니다 — iOS가 투명 픽셀을 검게 칠하기 때문입니다.
- 도형 수치는 `src/shared/ui/brand/keywi-geometry.ts` 한 곳에만 둡니다.

**`SITE.url`은 아직 `vercel.app` 주소입니다.** 도메인을 사기 전에 바꾸면 `metadataBase`를
타고 canonical·sitemap·OG가 전부 없는 주소를 가리켜 색인이 깨집니다.

이름 교체가 닿지 않은 곳이 있습니다. **GitHub 레포와 Vercel 프로젝트는 여전히
`trending-on-naver`** 입니다. CLI 인자로 쓰이므로 헷갈리지 마세요.

### 1-14. 도메인 연결과 SEO 기반 (2026-08-28)

**`keywi.kr`을 가비아에서 등록해 Vercel에 연결했습니다.**

- 정식 주소는 **apex(`https://keywi.kr`)** 입니다. `www.keywi.kr`과 `http://`는 둘 다
  308 영구 리다이렉트로 apex에 합쳐집니다. 색인이 한 주소로 모입니다.
- DNS는 가비아에 두고 A/CNAME만 Vercel로 넘깁니다(네임서버 위임 아님). 나중에 메일을
  붙이더라도 레코드 관리가 한곳에 남습니다.
- ⚠️ 가비아 DNS 관리는 **CNAME 값 끝에 마침표가 필수**입니다. 해외 등록기관은 반대라
  헷갈리기 쉽습니다.
- A 레코드는 `216.198.79.1`입니다. 흔히 알려진 `76.76.21.21`은 옛 값이고, Vercel은
  대역이 여러 개입니다 — **대시보드가 주는 값을 그대로 쓰세요.**

**검색엔진 등록을 마쳤습니다.**

- 구글 서치 콘솔 — DNS TXT로 인증(도메인 속성). 사이트맵 제출 완료.
- 네이버 서치어드바이저 — HTML 태그로 인증. 사이트맵 제출 완료.
  태그는 `layout.tsx`의 `metadata.verification`에 있습니다.
- ⚠️ 네이버는 **http와 https를 다른 사이트로 취급**합니다. `https://`로 등록해야 합니다.

**JSON-LD 구조화 데이터를 넣었습니다.**

- 홈 — `WebSite` + `ItemList`, 검색어 상세 — `BreadcrumbList`
- 셋 중 **검색 결과 모양을 실제로 바꾸는 건 `BreadcrumbList`뿐입니다.** `ItemList`는

### 1-16. AdSense 신청 준비 (2026-08-28)

- 문의 메일을 `nukko.team@gmail.com`으로 넣고 `mailto:` 링크를 걸었습니다.

- `/ads.txt`를 라우트로 만들었습니다. 없으면 AdSense가 수익 손실 위험을 경고합니다.

⚠️ **AdSense 스크립트는 `next/script`로 넣으면 안 됩니다.** `afterInteractive` 전략을 쓰면
`<head>`에는 preload 링크만 남고 실제 `<script>`는 하이드레이션 후 JS로 주입됩니다. 구글은

평범한 `<script>` 엘리먼트로 서버 HTML에 직접 찍습니다.

개인정보처리방침은 이미 요건을 충족하고 있었습니다. 제3자 쿠키, 맞춤광고 해제 안내,
Google AdSense 명시가 들어가 있습니다.

**2026-08-28 심사 신청 완료.** 게시자 ID `ca-pub-1007417880949310`, 소유권은 ads.txt
스니펫으로 확인했습니다. 환경 변수 등록과 재배포까지 마쳤고 `/ads.txt`와 `<head>` 스크립트가

#### 자동 광고를 쓰지 않기로 했습니다

AdSense 콘솔의 **자동 광고는 끈 채로 둡니다.** 수동 광고 단위로 갑니다.

- `AdSlot`이 세 규격의 높이를 미리 확보하고 있어 광고가 들어와도 레이아웃이 밀리지 않습니다.
  자동 광고는 구글이 임의 위치에 넣으므로 이 설계가 무의미해지고, 둘 다 켜면 지면이

- 실시간 순위를 몇 초 훑고 나가는 서비스라 오버레이·앵커 광고의 체감 손해가 큽니다.

주간 방문자 30명 규모에서 수익 차이는 어느 쪽이든 무의미하므로, 사용 경험과 속도를 지키는
쪽을 택했습니다. 나중에 자동 광고로 갈아타려면 콘솔 토글 하나면 됩니다.

### 1-18. AdSense 반려와 실시간성 재수정 (2026-09-14)

**AdSense가 "가치가 별로 없는 콘텐츠"로 반려됐습니다.** 라이브를 점검한 결과 원인은 둘입니다.

1. 화면의 텍스트가 전부 외부 데이터입니다 — 구글 트렌드 검색어, 언론사 뉴스 제목, 데이터랩
   그래프. 직접 만든 콘텐츠가 없습니다.
2. 검색어 상세 페이지가 순위에서 빠지는 즉시 `noindex` 빈 페이지가 됩니다. 사이트맵에
   올라간 URL을 따라가도 `200` + `noindex`가 나오는 걸 확인했습니다. 오래 남는 페이지는 5개뿐입니다.

대응으로 2절 '보류'였던 **검색어 이력 저장을 재개**합니다. DB는 Supabase(아래 순위 1).

같은 날 **홈의 실시간 순위가 1\~2시간씩 묵어 있던 문제**도 다시 고쳤습니다. 1-10절의 해법이
실제로는 동작하지 않고 있었습니다.

- **GitHub Actions `*/10`이 2\~5시간에 한 번 돌았습니다.** 실행 기록(UTC)이 `00:30 → 05:01 →
09:16 → 12:55 → 16:09 …`였습니다. GitHub는 무료 예약 작업을 부하에 따라 미루거나 건너뜁니다.
  그 사이 ISR은 첫 방문자에게 옛 페이지를 줬습니다(실측 `age: 1218` / `STALE`).
- **클라이언트 폴링이 마운트 직후엔 돌지 않았습니다.** `setInterval`만 걸어 첫 60초 동안은
  옛 시각이 그대로 보였습니다.

수정:

- 홈을 `dynamic = 'force-dynamic'`으로 요청마다 렌더. fetch에 `revalidate: 60`을 명시하고 있어
  데이터 캐시는 유지됩니다(Next 15 `patch-fetch.js`는 명시 설정이 없을 때만 캐시를 끔).
  구글 RSS 호출은 여전히 1분에 한 번입니다.
- `TrendingSearches`가 마운트 즉시 한 번 갱신. ISR로 캐시된 상세 페이지 사이드바도 곧바로 최신이 됩니다.
- `refresh-trending.yml` 삭제. 홈이 동적이라 캐시를 데울 필요가 없습니다.

### 1-19. 검색어 이력 저장 — Supabase (2026-09-14)

순위에서 내려간 검색어 페이지를 살려 두기 위해 **영속 계층을 처음 들였습니다.**

- **DB**: Vercel Marketplace로 Supabase 무료 플랜(`keywi-db`, 리전 `iad1` — Vercel 함수와 같은 곳).
  환경 변수는 연동이 Production/Preview/Development에 자동 등록합니다.
- **스키마** `db/migrations/001_keyword_history.sql` — 적용 완료.
  - `snapshots` / `snapshot_items`: 순위 목록이 **바뀔 때만** 한 줄. 같으면 `checked_at`만 갱신.
  - `keywords`: 검색어별 요약(처음·마지막 등장, 최고 순위, 최고 검색량, 마지막 뉴스, 진입 횟수).
  - RLS를 켜고 anon/authenticated 권한을 회수했습니다. 앱은 `postgres` 역할로 직접 붙습니다.
- **수집** `POST /api/collect` — `CRON_SECRET` Bearer 인증. RSS가 비면 기록하지 않고 502.
- **주기 호출** `db/migrations/002_collect_schedule.sql` — Supabase `pg_cron`이 `pg_net`으로
  호출합니다. 토큰은 Vault(`keywi_cron_secret`)에 넣었고 파일에는 적지 않습니다.
  처음엔 5분 주기였고 같은 날 1분으로 바꿨습니다(1-20절).
- **화면**: `/keyword/[keyword]`는 순위권이면 실시간 데이터, 아니면 DB 기록으로 렌더합니다
  ("최고 N위 · YYYY년 M월 D일까지 순위권"). 한 번도 순위에 오른 적 없는 검색어만 not-found.
  OG 이미지와 사이트맵도 DB 기록을 씁니다. **홈은 DB에 의존하지 않습니다** — DB 장애가 순위 표시를 막지 않게.
- 드라이버는 `postgres@3.4.9`(버전 고정). supabase-js 대신 SQL로 upsert·집계를 씁니다.

구현 중 겪은 함정:

- **`${JSON.stringify(x)}::jsonb`는 이중 인코딩됩니다.** postgres.js가 파라미터를 jsonb로 추론해
  문자열을 한 번 더 JSON으로 감싸 **배열 대신 문자열 스칼라**가 저장됩니다. `::text::jsonb`로 넘깁니다.
- **Vercel 연동이 주는 `POSTGRES_URL`의 `supa=` 쿼리**를 postgres.js가 서버 설정값으로 넘기므로
  `db.ts`에서 쿼리를 떼고 SSL은 옵션으로 줍니다. 풀러(6543)라 `prepare: false`.
- bigint(`id`)는 문자열로 옵니다.
- 로컬 검증 중 `pkill -f "next start"`가 `next-server` 프로세스를 못 잡아 **옛 서버가 포트를 쥔 채
  옛 코드로 응답**했습니다. 새 서버 로그 첫 줄이 `EADDRINUSE`인지 확인하세요.

### 1-20. 기록 해석 문장·날짜별 기록, 수집 1분 주기 (2026-09-14)

AdSense "가치가 별로 없는 콘텐츠" 대응의 첫 단계로, 쌓이는 이력에서 **검색어마다 달라지는 문장**을 만듭니다.

- **검색어 상세 "이 검색어의 기록"** — 처음 등장 시각, 최고 순위·검색량, 진입 횟수, 순위권 체류
  시간, 현재 순위 또는 마지막 확인 시각. 네이버 30일 추이는 최고점 날짜와 최근 7일 증감으로 해석합니다.
  증감이 3배를 넘으면 "1,527%" 대신 "약 16배"로 씁니다. 은/는은 받침으로 고릅니다.
- **`/daily`, `/daily/YYYY-MM-DD`** — 그날(KST) 순위에 오른 검색어를 최고 순위·체류 시간 순으로.
  앞에 요약 문장("모두 N개", "가장 오래 머문 검색어", "1위에 오른 검색어")을 둡니다.
  이전·다음 날 이동, 헤더 메뉴 "날짜별 기록", 사이트맵 포함. 기록 없는 날짜는 `noindex`.
- 체류 시간은 스냅샷을 구간으로 펼쳐 계산합니다. 스냅샷은 다음 스냅샷까지 유효하되 `checked_at + 2분`에서
  끊어 수집이 멈춘 구간을 순위권으로 치지 않습니다.

**구글 RSS 갱신 주기를 실측했습니다**(30초 간격 25분). 목록 교체는 09:35 → 09:43 → 09:53으로
약 8\~10분 간격이었고, 교체 뒤 1\~2분 사이에 순위·검색량을 고치는 작은 변경이 두 번 있었습니다
(09:44, 09:55 — 폴란드 검색량 10000+ → 200+).

**화면 지연을 잘못 알고 있었습니다.** "구글이 바꾸면 1분 안에 반영"이 아니었습니다. fetch 데이터
캐시도 stale-while-revalidate라(`patch-fetch.js`의 `entry.isStale` 분기) 만료된 응답을 먼저 내줍니다.
방문자가 뜸하면 수집 요청이 사실상 캐시를 데우므로 **5분 주기일 때 화면이 최대 약 5분 늦었습니다**
(09:35:00 수집은 옛 목록, 3초 뒤 로컬 측정은 새 목록). 화면의 "업데이트" 시각도 렌더 시각이라 실제보다
새것처럼 보였습니다.

- 수집을 **1분 주기**로 변경(`* * * * *`, 적용 완료). 짧은 보정도 기록되고 화면 지연은 최대 1\~2분.
- "업데이트" 시각을 **구글 응답의 `Date` 헤더**로 변경(`getTrendingSnapshot`). 캐시된 응답도 헤더를 보존합니다.

### 1-21. 글 목록·상세 페이지 (2026-09-14)

AdSense 재신청의 가장 확실한 대응인 **직접 쓴 글**을 올릴 자리를 만들었습니다.

- 글은 `content/articles/<slug>.md` 마크다운 파일 하나 = 글 하나. 맨 위에 `title`·`description`·`date`.
  작성 규칙·이미지 경로(`public/images/articles/<slug>/`)·초안 사용법은 `content/articles/README.md`.
- `/articles` 목록(최신순, 날짜·읽는 시간), `/articles/[slug]` 상세(작성자·게시일·수정일, Article 구조화 데이터,
  광고 지면, 다른 글 3개). 없는 주소는 `dynamicParams = false`로 진짜 404.
- 본문 스타일은 `ArticleProse`(약관용 `Prose`와 별도). 표는 모바일에서 표만 가로 스크롤, 외부 링크는 새 탭.
- **글이 0개면 헤더 '글' 메뉴·사이트맵 항목이 없고 `/articles`는 noindex** — 빈 페이지가 미완성으로 보이지 않게.
  첫 글 파일이 올라가면 자동으로 나타납니다.

## 3. 알고 있는 문제

곧바로 고칠 것은 아니지만 인지하고 있어야 하는 것들입니다.

**한 번도 순위에 오르지 않은 검색어는 soft 404입니다.** `notFound()`를 호출하지만 ISR 캐시를
거치면서 HTTP 상태가 200으로 나갑니다(Next.js의 알려진 동작). `generateMetadata`가
`noindex, nofollow`를 붙이므로 색인되지는 않습니다. `dynamicParams = false`로 바꾸면 진짜
404가 되지만, 그러면 빌드 이후 새로 뜬 검색어가 전부 404가 되므로 **쓰면 안 됩니다.**
순위에서 내려간 검색어는 이제 DB 기록으로 렌더되므로(1-19절) 해당하지 않습니다.

**Supabase 무료 플랜은 7일간 활동이 없으면 프로젝트를 일시정지합니다.** 1분마다 수집이
돌므로 평소엔 걸리지 않지만, cron이 멈추면(배포 주소 변경, Vault 토큰 불일치로 401 등)
DB까지 연쇄로 멈출 수 있습니다. 상세 페이지가 순위권 검색어만 나오면
`cron.job_run_details`와 `net._http_response`부터 확인하세요.

**네이버 무료 쿼터에는 조건이 있습니다.** 콘솔에 보이는 "당월 50,000회"는 기본 무료
30,000건과 한시적 무료 20,000건을 합친 값입니다. 뒤쪽 구간은 분류상 '유료'라 언젠가
과금될 수 있으므로, **안정적으로 기댈 수 있는 값은 30,000건으로 잡는 편이 안전합니다.**
문서상 429는 "하루 허용량 초과"로 설명되어 있어 일 한도도 있을 수 있습니다.

**`next`가 고정한 내부 의존성에 취약점 5건이 남아 있습니다.** `postcss@8.4.31`,
`sharp@0.34.5`. 우리 쪽에서 버전을 올릴 수 없고, `pnpm.overrides`로 강제하는 방법은 Next의
CSS 파이프라인에 영향을 줄 수 있어 택하지 않았습니다. Next를 올리면 함께 해소됩니다.

**Next.js 16이 나와 있습니다.** 지금은 15.5.23(15.x 백포트 라인)입니다. 배포 복구가
목적이라 메이저 업그레이드는 하지 않았습니다. 여유가 생기면 별도로 진행하세요.

**주기 작업에 GitHub Actions 스케줄을 쓰지 마세요.** 실행 시각이 보장되지 않아 `*/10`이
실제로는 2\~5시간 간격이었고(1-18절), 레포에 60일간 커밋이 없으면 자동 비활성화까지 됩니다.
`refresh-trending.yml`은 삭제했습니다. 정확한 주기가 필요한 작업은 Supabase `pg_cron`으로 돌립니다.
