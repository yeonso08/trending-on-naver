## 1. 지금까지 한 일

### 1-1. 폰트 정리

`next/font`의 Inter를 쓰면서 `globals.css`가 `body`에 Arial을 다시 지정해 서로 충돌하고
있었습니다. 한글 폰트는 지정된 적이 없었습니다.

**Pretendard Variable**(SIL OFL 1.1, 상업적 이용 가능)로 교체하고 자체 호스팅합니다.
전체 variable 파일은 2MB라 통짜로 쓰지 않고 **동적 서브셋 92개**를 넣었습니다.
브라우저가 `unicode-range`를 보고 필요한 조각만 받습니다.

- 메인 페이지 기준 실제 다운로드: **8개 / 약 206KB** (통짜 대비 10배 절감)
- 사용 빈도 상위 3개(라틴 + 최빈 한글)는 preload
- 외부 CDN을 쓰지 않아 추가 DNS/TLS 왕복이 없습니다

### 1-8. 함께 고친 버그

- **`generateStaticParams` 이중 인코딩** — 이미 `encodeURIComponent`된 slug를 넘겨
  Next.js가 한 번 더 인코딩했습니다. **한글 검색어 페이지 10개 중 9개가 not-found로
  프리렌더**되고 있었고, 라틴 문자 검색어(`mlb`)만 멀쩡해 발견이 어려웠습니다.
- **`Loading.tsx` → `loading.tsx`** — Next.js는 소문자만 인식합니다. macOS는 대소문자를
  구분하지 않아 로컬에선 동작하는 것처럼 보였지만 Vercel(Linux)에선 적용되지 않았습니다.
- **`DeviceType`의 `'m'` → `'mo'`** — 네이버 실제 스펙은 `pc`/`mo`이고 폼은 이미 `mo`를
  보내고 있어서, 모바일 선택 시 검색 조건 표시가 `undefined`였습니다.
- **검색 폼 기본값** — 날짜가 비어 있고 연령대가 하나도 선택되지 않아 처음 열면 검증
  실패부터 보게 됐습니다. 최근 30일 + 전체 연령대로 시작합니다.
- **구글 RSS 실패가 빌드를 깨뜨리던 문제** — 조회 실패 시 예외를 던져 프리렌더 단계가
  통째로 실패했습니다. 빈 배열 반환 + 10초 타임아웃으로 바꿨습니다.
- 죽은 코드 제거: `use-trend-data.ts`(POST 라우트에 GET 호출), `trending-detail.tsx`,
  `shared/api/base.ts`와 `axios` 의존성, 잔존 `console.log`

### 1-10. 실시간성 복구 (2026-08-26)

"실시간 검색어"인데 화면의 기준 시각이 한 시간 넘게 뒤처져 있었습니다. 원인이 셋이었습니다.

1. **타임존 미지정** — `Intl.DateTimeFormat`에 `timeZone`이 없어 UTC로 도는 서버 기준으로
   포맷됐습니다. 로컬(KST)에선 멀쩡해 보여 발견이 어려웠습니다.
2. **표시 시각의 의미가 틀림** — 구글 RSS의 `pubDate`(그 검색어가 트렌드에 오른 시각)를
   "○○ 기준"으로 찍고 있었습니다. 우리가 언제 갱신했는지와 무관한 값입니다.
   서버가 실제로 데이터를 가져온 시각(`fetchedAt`)으로 바꿨습니다.
3. **ISR 캐시 정체** — `revalidate: 60`은 자동 갱신이 아니라 stale-while-revalidate입니다.
   방문자가 뜸하면 아무도 재생성을 트리거하지 않아 캐시가 수십 분씩 묵습니다.
   실측으로 `age: 2333`(39분) / `x-vercel-cache: STALE`을 확인했습니다.

3번은 두 축으로 해결했습니다.

- **`.github/workflows/refresh-trending.yml`** — 10분마다 홈페이지에 `curl`. **Vercel Hobby는
  자체 Cron이 하루 1회 제한**이라 못 쓰고, 퍼블릭 레포의 무료 GitHub Actions로 대신합니다.
- **60초 클라이언트 폴링** — `GET /api/trending`. 이미 열어 둔 탭이 새로고침 없이 갱신됩니다.
  내부 fetch가 같은 60초 캐시를 타므로 구글 RSS 호출은 늘지 않습니다. 백그라운드 탭은 건너뜁니다.

### 1-13. 브랜드 교체 (2026-08-28)

**서비스명을 '트렌드나우'에서 '키위(Keywi)'로 바꿨습니다.** 이전 이름은 실시간 순위만
가리켜서 트렌드 분석 기능을 담지 못했습니다. '키워드 순위'를 줄인 이름입니다.

로마자는 `Kiwi`가 아니라 **`Keywi`** 입니다. 철자에 `key`가 남아 어원이 스스로 드러나고,
과일 `kiwi` 및 기존 키위 브랜드들(키위플러스·키위웍스·키위디스크 등)과 검색 결과가
갈립니다. 이 표기를 되돌리면 두 이점이 한꺼번에 사라집니다.

**로고는 '지평선 위로 떠오른 반단면'입니다.** 키위 단면이면서 부채꼴 차트로도 읽혀
실시간 순위와 추이 분석을 한 형태에 담습니다. 여섯 갈래 시안을 놓고 고른 결과입니다.

- 과육 · 부챗살 · 씨앗이 톤을 달리하는 **세 겹 구조**이고 이 톤 차이가 인상을 만듭니다.
  두 색으로 줄여 네거티브로 파내 본 적이 있는데 딱딱해져서 되돌렸습니다.
- **배경 타일은 없습니다.** 심볼만 배경 위에 얹습니다. 다크 모드를 따라가도록 과육 톤을
  `--brand-flesh` 토큰으로 뽑았고, 파비콘에는 `prefers-color-scheme`를 심었습니다.
- 애플 아이콘만 배경을 깝니다 — iOS가 투명 픽셀을 검게 칠하기 때문입니다.
- 도형 수치는 `src/shared/ui/brand/keywi-geometry.ts` 한 곳에만 둡니다.

**`SITE.url`은 아직 `vercel.app` 주소입니다.** 도메인을 사기 전에 바꾸면 `metadataBase`를
타고 canonical·sitemap·OG가 전부 없는 주소를 가리켜 색인이 깨집니다.

이름 교체가 닿지 않은 곳이 있습니다. **GitHub 레포와 Vercel 프로젝트는 여전히
`trending-on-naver`** 입니다. CLI 인자로 쓰이므로 헷갈리지 마세요.

### 1-14. 도메인 연결과 SEO 기반 (2026-08-28)

**`keywi.kr`을 가비아에서 등록해 Vercel에 연결했습니다.**

- 정식 주소는 **apex(`https://keywi.kr`)** 입니다. `www.keywi.kr`과 `http://`는 둘 다
  308 영구 리다이렉트로 apex에 합쳐집니다. 색인이 한 주소로 모입니다.
- DNS는 가비아에 두고 A/CNAME만 Vercel로 넘깁니다(네임서버 위임 아님). 나중에 메일을
  붙이더라도 레코드 관리가 한곳에 남습니다.
- ⚠️ 가비아 DNS 관리는 **CNAME 값 끝에 마침표가 필수**입니다. 해외 등록기관은 반대라
  헷갈리기 쉽습니다.
- A 레코드는 `216.198.79.1`입니다. 흔히 알려진 `76.76.21.21`은 옛 값이고, Vercel은
  대역이 여러 개입니다 — **대시보드가 주는 값을 그대로 쓰세요.**

**검색엔진 등록을 마쳤습니다.**

- 구글 서치 콘솔 — DNS TXT로 인증(도메인 속성). 사이트맵 제출 완료.
- 네이버 서치어드바이저 — HTML 태그로 인증. 사이트맵 제출 완료.
  태그는 `layout.tsx`의 `metadata.verification`에 있습니다.
- ⚠️ 네이버는 **http와 https를 다른 사이트로 취급**합니다. `https://`로 등록해야 합니다.

**JSON-LD 구조화 데이터를 넣었습니다.**

- 홈 — `WebSite` + `ItemList`, 검색어 상세 — `BreadcrumbList`
- 셋 중 **검색 결과 모양을 실제로 바꾸는 건 `BreadcrumbList`뿐입니다.** `ItemList`는
  구글이 캐러셀로 만들어 주는 타입이 정해져 있어 이 콘텐츠로는 시각적 변화가 없습니다.
  기대치를 낮게 잡으세요.
- `JsonLd` 컴포넌트는 직렬화 결과의 `<`를 이스케이프합니다. 실시간 검색어는 외부에서 오는
  값이라 `</script>`가 섞이면 문서가 깨집니다.

### 1-16. AdSense 신청 준비 (2026-08-28)

- 문의 메일을 `nukko.team@gmail.com`으로 넣고 `mailto:` 링크를 걸었습니다.
- **점선 자리표시자를 걷어냈습니다.** `AdSlot`은 이제 게시자 ID와 광고 단위 ID가 둘 다
  있을 때만 렌더합니다. 빈 상자가 남아 있으면 심사에서 미완성으로 보입니다.
- 게시자 ID는 `NEXT_PUBLIC_ADSENSE_CLIENT` 환경 변수로 받습니다. 없으면 `<head>` 스크립트도
  `/ads.txt`도 나가지 않습니다.
- `/ads.txt`를 라우트로 만들었습니다. 없으면 AdSense가 수익 손실 위험을 경고합니다.
  게시자 ID에서 만들어 내며 `ca-` 접두사를 뗀 형태로 적습니다.

세 경로를 모두 확인했습니다 — ID 없음(아무것도 안 나감), ID 있음(스크립트와 ads.txt 정상),
ID는 있고 slot은 비어 있음(지면 렌더 안 함).

개인정보처리방침은 이미 요건을 충족하고 있었습니다. 제3자 쿠키, 맞춤광고 해제 안내,
Google AdSense 명시가 들어가 있습니다.

### 순위 1 — AdSense 신청 (수익화의 전제)

> 10여 개뿐이고 순위가 바뀌면 교체됩니다. 검색어 이력 저장은 하지 않기로 했으므로(아래
> '보류' 항목), 일단 지금 상태로 신청해 보고 반려되면 그때 대응하는 편이 낫습니다.

## 3. 알고 있는 문제

곧바로 고칠 것은 아니지만 인지하고 있어야 하는 것들입니다.

**순위 밖 검색어가 soft 404입니다.** `notFound()`를 호출하지만 ISR 캐시를 거치면서 HTTP
상태가 200으로 나갑니다(Next.js의 알려진 동작). `generateMetadata`가 `noindex, nofollow`를
붙이므로 색인되지는 않습니다. `dynamicParams = false`로 바꾸면 진짜 404가 되지만, 그러면
빌드 이후 새로 뜬 검색어가 전부 404가 되므로 **쓰면 안 됩니다.** 근본 해결은 검색어 이력
저장인데 하지 않기로 했으므로(2절 '보류' 항목), 이 상태로 둡니다. 색인은 막혀 있어 실질
피해는 없습니다.

**네이버 무료 쿼터에는 조건이 있습니다.** 콘솔에 보이는 "당월 50,000회"는 기본 무료
30,000건과 한시적 무료 20,000건을 합친 값입니다. 뒤쪽 구간은 분류상 '유료'라 언젠가
과금될 수 있으므로, **안정적으로 기댈 수 있는 값은 30,000건으로 잡는 편이 안전합니다.**
문서상 429는 "하루 허용량 초과"로 설명되어 있어 일 한도도 있을 수 있습니다.

**`next`가 고정한 내부 의존성에 취약점 5건이 남아 있습니다.** `postcss@8.4.31`,
`sharp@0.34.5`. 우리 쪽에서 버전을 올릴 수 없고, `pnpm.overrides`로 강제하는 방법은 Next의
CSS 파이프라인에 영향을 줄 수 있어 택하지 않았습니다. Next를 올리면 함께 해소됩니다.

**Next.js 16이 나와 있습니다.** 지금은 15.5.23(15.x 백포트 라인)입니다. 배포 복구가
목적이라 메이저 업그레이드는 하지 않았습니다. 여유가 생기면 별도로 진행하세요.

**GitHub Actions 스케줄은 조용히 멈출 수 있습니다.** `refresh-trending.yml`은 두 가지
제약이 있습니다. ① 실행 시각이 보장되지 않아 GitHub 부하에 따라 몇 분 밀립니다.
② **레포에 60일간 커밋이 없으면 GitHub가 스케줄 워크플로우를 자동 비활성화합니다.**
방치되기 쉬운 개인 프로젝트라 특히 걸리기 쉬운 조건입니다. 실시간 순위가 오래 묵어
보이면 Actions 탭에서 워크플로우가 살아 있는지부터 확인하세요.
